# Plan the PR structure

A reviewer can approve a PR from its description only when the PR does one thing. Small, single-purpose PRs are also reviewed faster and more thoroughly, introduce fewer bugs, are cheaper to reject, and are simpler to roll back.

Splitting is cheap before the code exists and expensive afterwards. So this skill runs at **planning time**: before you write code for anything larger than a small fix, and again whenever the work grows past its plan. Splitting an existing branch (step 6) is the fallback.

## 1. What one PR is

One PR is **one self-contained change**:

- **One reason.** Its purpose fits in one sentence without "and". A refactor and a behavior change are two reasons. A bug fix plus an unrelated cleanup is two reasons.
- **Complete for that reason.** It includes the tests for its behavior. A new API arrives with at least one real caller, so a reviewer can judge the API by its use and no unused code lands.
- **Safe to merge alone.** After it merges, the build passes and the system works for users and developers, even if the next PR never lands.
- **Understandable alone.** Everything a reviewer needs is in the PR, its description, the existing code, or a PR they already reviewed.
- **Not too small.** If a PR is so small that its purpose is unclear without the next one, merge the two.

Size is a signal, not the rule. As rough anchors from Google's guide: about 100 changed lines is usually fine, about 1,000 is usually too large, and 200 lines across 50 files is larger than 200 lines in one file. Deleting a whole file, or a change generated by a tool the reviewer trusts, counts for much less than its line count.

When in doubt, make it smaller. The author always overestimates how much context the reviewer has.

## 2. Write the plan before the code

For any work that is not obviously one PR, write a short plan and show it to the user before coding. Keep it in the repository's usual place for plans, or in the session if there is none.

```markdown
# <goal>

End state: <one or two sentences: what is true when every PR has merged>.

| # | PR | Reason (one sentence) | Depends on | Leaves the system | Verified by | Risk |
|---|----|-----------------------|------------|-------------------|-------------|------|
| 1 | Add tests for current retry behavior | Pin today's behavior before changing it | - | Unchanged | New tests pass on main | Low |
| 2 | Extract RetryPolicy interface | Make the policy replaceable; no behavior change | 1 | Unchanged | Tests from 1 still pass | Low |
| 3 | Add exponential backoff policy behind flag | Stop retry storms after overload | 2 | Unchanged with flag off | Unit tests; staging with flag on | Medium |
| 4 | Turn on backoff in production | Roll out the fix | 3 | New behavior | Dashboards for one week | Medium |
| 5 | Remove the old policy and the flag | Clean up | 4 | Unchanged | Tests | Low |

Open questions: <decisions the user should make before PR 1>.
```

For each row, check:

- The reason has no "and".
- "Leaves the system" is a working state. "Half-migrated, do not deploy" is not.
- Each PR can be described without referring to a PR that comes after it, except to say what is out of scope.

Ask the user to confirm the plan when it involves more than two or three PRs, or when the order is a real choice (for example, whether to ship behind a flag). Then follow it.

## 3. Ways to split

Pick the split that gives each PR one reason and a working system. Usually several apply at once.

- **Refactor first, then change behavior.** Moving, renaming, or extracting code goes in its own PR with no behavior change. The behavior change that follows is then small and easy to see. Small cleanups, such as renaming a local variable, can stay inside the behavior PR.
- **Tests first.** When you are about to change code that has weak tests, add tests that pin the current behavior in a PR of their own. The later PR then shows exactly which test expectations change. Test infrastructure (helpers, a new integration harness) can also go first.
- **Interface, then implementations.** Land a shared interface, schema, proto, or stub with its first caller. Then implement each side in separate PRs, which can be reviewed in parallel. This is Google's "horizontal" split: by layer.
- **Vertical slices.** Deliver one narrow feature end to end (for example multiplication, then division), each slice through every layer. Slices can proceed in parallel and each is independently useful.
- **Expand, migrate, contract.** For a change to a stored format, schema, or public API that has existing users: add the new form beside the old, move readers and writers over, then remove the old form. Each step is one PR and each leaves the system working. This is the standard way to avoid a big-bang migration.
- **Code, then config.** Ship the code with the new behavior off (a flag or config default), then turn it on in a separate PR. Config often deploys faster than code and is easier to roll back on its own.
- **By reviewer.** Changes that need different owners (for example a proto and the service that uses it) can go in separate PRs reviewed at the same time. Tell each set of reviewers about the other PR.

Combine directions when the work is large: a table of layers by features, where each cell is one PR, built from the bottom layer up.

## 4. Stack, so splitting does not block you

Waiting for review on PR 1 before starting PR 2 wastes time. Instead:

- **Stack:** start PR 2 on a branch based on PR 1's branch. Each PR targets the branch below it. Keep stacks shallow, about two to four layers, because each layer adds rebase work.
- **Work in parallel:** use the independent rows of the plan (different layers, different slices) while one PR is in review.
- **Keep every layer green.** Each layer must build and pass tests on its own, because it may merge on its own. Run the tests on each layer, not only on the top one.

If the repository has a stacking tool or a skill for it, use that for the mechanics.

## 5. While coding: keep the PR to its reason

Most oversized PRs were planned as small and grew. While you work:

- **Commit along the plan.** One or more commits per planned PR, never one commit that spans two.
- **When you find unplanned work** (a bug next door, a cleanup, a missing test helper), do not fold it in. Note it, and either make it a separate small PR or add a row to the plan. Tell the user if it changes the plan.
- **Record decisions as you make them.** For each PR, keep a few lines on what you chose, what you rejected, and why. The description skill needs this, and it is not recoverable from the diff later. A short `decisions` list in the plan file, or in commit bodies, is enough.
- **Check the size.** Run `git diff --stat <base>...HEAD` at natural stopping points. If the branch has grown past its reason, or well past the size you planned, stop and re-plan before writing more.

## 6. Split an existing large branch

When the code already exists as one branch:

1. Read the whole diff and group the hunks by reason: refactor, tests for existing behavior, new interface, each behavior change, config, cleanup.
2. Order the groups by dependency, using the strategies in step 3. Write the plan as in step 2 and show it to the user.
3. Build each PR's branch from the base:

   ```bash
   git switch -c part-1 <base>
   git checkout <big-branch> -- path/to/file      # whole files that belong to this part
   git checkout -p <big-branch> -- path/to/file   # only some hunks of a file (interactive; if that is not available, edit the file by hand)
   git commit
   ```

   Or, if the branch's commits already follow the groups, `git cherry-pick` them in order onto new branches.
4. Make each branch build and pass tests on its own. Splitting often reveals a hidden dependency. When it does, move the dependency to an earlier part rather than letting a part break the build.
5. Confirm nothing was lost: the last part, with all earlier parts merged in, should match the original branch (`git diff <big-branch> part-N` is empty, or differs only in ways you can explain).

## 7. When a large PR is acceptable

Rarely. Generated changes from a trusted tool, file deletions, and mechanical renames done by a tool can be large if they contain nothing else. If a hand-written change truly cannot be split, tell the user and the reviewers before the review starts, not when the PR appears, and expect a longer review. First try preceding it with a refactor-only PR that makes the main change smaller.

## 8. Hand-off to the description

Each PR's description (see the `write-pr-description` skill) should:

- State its one reason in the opening.
- Say which part of the plan it is and link the plan or the previous PR, when it is part of a series.
- List the later parts under "Out of scope" so the reviewer does not ask for them here.
- Use the decisions you recorded in step 5.

## Anti-patterns

- **"Phase 1" PRs with no caller.** Code that nothing uses cannot be judged and may never be used. Ship an interface with its first real caller.
- **Splitting by file type.** "All the protos", then "all the handlers", where neither builds without the other. Split by reason, and keep each part working.
- **Mixing a move with a change.** Moving a function to a new file and changing it in the same PR hides the change inside the move.
- **A refactor that changes behavior "slightly".** Then it is not a refactor. Split the behavior change out.
- **Splitting after review starts.** Reviewers lose their comments and context. Plan first.
- **Too small to understand.** Three PRs of 20 lines that only make sense together are one PR.
