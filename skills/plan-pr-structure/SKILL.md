# Plan the PR structure

A reviewer can approve a PR from its description only when the PR does one thing. Small, single-purpose PRs are also reviewed faster and more thoroughly, introduce fewer bugs, are cheaper to reject, and are simpler to roll back.

Splitting is cheap before the code exists and expensive afterwards, so this skill runs at **planning time**, and again whenever the work grows past its plan. Splitting an existing branch (step 5) is the fallback.

## Works with pstack

This skill assumes [pstack](https://github.com/cursor/plugins/tree/main/pstack) is installed and does not repeat it. pstack's skills are user-invoked only, so read their `SKILL.md` files from where pstack is installed instead of calling them.

| Need | Use |
| --- | --- |
| The plan file: PR ids, landing order, dependency graph, per-PR checkboxes, verification | pstack poteto-mode playbook `multi-phase-plan` |
| Each unit ends in a checkable state; land the failing test before the fix | pstack `principle-sequence-verifiable-units` |
| Replacing an internal API | pstack `principle-migrate-callers-then-delete-legacy-apis` |
| Stacking PRs on each other's branches | pstack playbooks `opening-a-pr` and `autopilot-stack` |
| Recording decisions for the descriptions | pstack `show-me-your-work` |

This skill adds what those do not: what counts as one PR, how to choose the cut, scope discipline while coding, and how to split a branch that already exists. If pstack is not installed, write the plan as a short ordered list with each PR's reason, dependencies, and verification.

## 1. What one PR is

One PR is **one self-contained change**:

- **One reason.** Its purpose fits in one sentence without "and". A refactor and a behavior change are two reasons. A bug fix plus an unrelated cleanup is two reasons.
- **Complete for that reason.** It includes the tests for its behavior. A new API arrives with at least one real caller, so a reviewer can judge the API by its use and no unused code lands.
- **Safe to merge alone.** After it merges, the build passes and the system works for users and developers, even if the next PR never lands.
- **Understandable alone.** Everything a reviewer needs is in the PR, its description, the existing code, or a PR they already reviewed.
- **Not too small.** If a PR's purpose is unclear without the next one, merge the two.

Size is a signal, not the rule. As rough anchors from Google's guide: about 100 changed lines is usually fine, about 1,000 is usually too large, and 200 lines across 50 files is larger than 200 lines in one file. Deleting a whole file, or a change generated by a tool the reviewer trusts, counts for much less than its line count. When in doubt, make it smaller: the author always overestimates how much context the reviewer has.

Check every row of the plan against this list before showing the plan to the user.

## 2. Choose the cut

Pick the split that gives each PR one reason and a working system. Usually several apply at once.

- **Refactor first, then change behavior.** Moving, renaming, or extracting code goes in its own PR with no behavior change, so the behavior change that follows is small and easy to see. Small cleanups, such as renaming a local variable, can stay inside the behavior PR.
- **Tests first.** Before changing code with weak tests, land tests that pin the current behavior. The later PR then shows exactly which expectations change. Test infrastructure (helpers, a new harness) can also go first.
- **Interface, then implementations (by layer).** Land a shared interface, schema, proto, or stub with its first caller. Then implement each side in its own PR; these can be reviewed in parallel.
- **Vertical slices (by feature).** Deliver one narrow feature end to end through every layer, then the next. Each slice is useful alone, and slices can proceed in parallel.
- **Layers by features.** For large work, draw a table with layers as rows and features as columns. Each cell is one PR, built from the bottom layer up.
- **Code, then config.** Ship the code with the new behavior off (a flag or a config default), then turn it on in a separate PR. Config often deploys faster than code and rolls back on its own.
- **By reviewer.** Changes that need different owners (a proto and the service that uses it) can be separate PRs reviewed at the same time. Tell each set of reviewers about the other PR.
- **Compatibility across a boundary.** For an internal API with no outside users, follow pstack's migrate-callers-then-delete principle: no compatibility layer. When old and new must coexist, because of stored data, external consumers, or a rolling deploy where old and new binaries run together, use expand, migrate, contract: add the new form beside the old, move readers and writers, then remove the old form, one PR per step.

Ask the user to confirm the cut when the plan has more than two or three PRs, or when the order is a real choice, such as whether to ship behind a flag.

## 3. Keep each PR to its reason while coding

Most oversized PRs were planned small and grew.

- **Commit along the plan.** One or more commits per planned PR, never one commit that spans two.
- **Keep unplanned work out.** When you find a bug next door, a cleanup, or a missing helper, do not fold it in. Note it, and either make it a separate small PR or add it to the plan. Tell the user if it changes the plan.
- **Record decisions in the pstack decision log, not in the code.** The log is your working trail; most of it never reaches the PR. Code comments and commit messages describe the final code, not the iterations that led to it.
- **Check the size at natural stopping points** with `git diff --stat <base>...HEAD`. If the branch has grown past its reason, or well past the planned size, stop and re-plan before writing more.

## 4. Keep every layer green

When PRs stack, each layer must build and pass tests on its own, because it may merge on its own. Run the checks on each layer, not only the top one. Keep stacks shallow, about two to four layers, because every layer adds rebase work. Use independent rows of the plan to keep working while one PR is in review.

## 5. Split an existing large branch

When the code already exists as one branch:

1. Read the whole diff and group the hunks by reason: refactor, tests for existing behavior, new interface, each behavior change, config, cleanup.
2. Order the groups using step 2, write the plan, and show it to the user.
3. Build each part's branch from the base:

   ```bash
   git switch -c part-1 <base>
   git checkout <big-branch> -- path/to/file      # whole files that belong to this part
   git checkout -p <big-branch> -- path/to/file   # some hunks only (interactive; edit by hand where that is unavailable)
   git commit
   ```

   If the branch's commits already follow the groups, `git cherry-pick` them onto new branches instead.
4. Make each part build and pass tests on its own. Splitting often reveals a hidden dependency: move it to an earlier part rather than letting a part break the build.
5. Confirm nothing was lost: the last part, with all earlier parts beneath it, matches the original branch (`git diff <big-branch> part-N` is empty, or differs only in ways you can explain).

## 6. When a large PR is acceptable

Rarely. Generated changes from a trusted tool, file deletions, and tool-driven mechanical renames can be large if they contain nothing else. If a hand-written change truly cannot be split, first try preceding it with a refactor-only PR that makes it smaller. If it still cannot, tell the user and the reviewers before the review starts, and expect a longer review.

## 7. Hand-off to the description

Each PR's description (`write-pr-description`) states its one reason under Why, names its part of the plan with a link under Scope, lists the later parts as out of scope, and takes a tradeoff from the decision log only when a reviewer would otherwise ask "why not X?".

## Anti-patterns

- **"Phase 1" PRs with no caller.** Code nothing uses cannot be judged and may never be used. Ship an interface with its first real caller.
- **Splitting by file type.** "All the protos", then "all the handlers", where neither builds alone. Split by reason.
- **Mixing a move with a change.** Moving a function and changing it in one PR hides the change inside the move.
- **A refactor that changes behavior "slightly".** Then it is not a refactor. Split the behavior change out.
- **Splitting after review starts.** Reviewers lose their comments and context. Plan first.
- **Too small to understand.** Three 20-line PRs that only make sense together are one PR.
